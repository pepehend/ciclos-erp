# CiclosERP: guia para desenvolvimento

Repositório `pepehend/ciclos-erp` (antes `pepehend/sistema-gestao`; o GitHub redireciona o nome antigo). No cPanel, a pasta do clone continua `~/repositories/sistema-gestao`, e o `deploy/auto-deploy.sh` descobre a própria pasta sozinho.

Sistema de estoque, vendas e lucro em PHP 8 + MySQL, feito para hospedagem compartilhada (cPanel). Não há Composer nem etapa de build: os arquivos são enviados como estão.

## Arquitetura
- `api.php`: roteador JSON (`api.php?r=<rota>`). As rotas ficam num array `'METODO rota' => closure`. Todo POST exige o header `X-CSRF-Token` (obtido em `GET me`).
- `app/lib/*.php`: classes estáticas (`DB`, `Inventory`, `Invoices`, `Reports`, `Auth`, `Backup`, `Customers`, `Quotes`, `Settings`, `Finance`, `PurchaseOrders`). Erros mostrados ao usuário usam `AppError` (mensagem em português e status HTTP).
- Acesso por token (aplicativo Android, v3.4.0): `ApiTokens` (`app/lib/tokens.php`, tabela `api_tokens`, só o SHA-256 do token). `POST token_login` (e-mail, senha, `device`; sem CSRF, mesmo limite de tentativas do login, via `Auth::tokenLogin`/`verifyLogin`) devolve `token` (`cer_…`), `user`, `perms`, `perm_modules`. Os outros pedidos mandam `Authorization: Bearer <token>` (ou `X-Api-Token`; o `.htaccess` repassa o Authorization em CGI/FPM): `Auth::start()` preenche `Auth::$api` e `$_SESSION` em memória, sem cookie, e `checkCsrf()` não se aplica. Token expira com `IDLE_DAYS` (60) sem uso; até `MAX_PER_USER` (10) por usuário. `logout` apaga o token do aparelho; trocar a senha (`POST password`) apaga os outros; senha nova pelo admin (`user_save`) ou usuário excluído apagam todos; desativado perde o acesso. Minha conta → Aparelhos do aplicativo (`GET api_tokens`, `POST api_token_revoke`). `api_tokens` fica fora do `Backup::TABLES` (como `login_attempts`) e fora do `USER_REFS` (token não é histórico: não impede excluir o usuário).
- `assets/app.js`: SPA em JavaScript puro, com rotas por hash (`#/produtos`, `#/produto/12`…). Cada tela é uma função `viewX(container, ...args)`. Sempre use `esc()` ao interpolar dados em HTML.
- Banco: MySQL em produção e SQLite nos testes. O schema fica em `DB::schema()`. O SQL precisa funcionar nos dois (datas como strings `Y-m-d H:i:s` geradas no PHP e parâmetros `?`).

## Regras de negócio importantes
- Toda alteração de estoque passa por `Inventory::move()`, que trava a linha (`FOR UPDATE`), recalcula o custo médio em entradas e grava em `movements` com o saldo.
- As vendas gravam `unit_cost` no momento da venda; os relatórios de lucro usam esse valor.
- Venda direta (`viewNewSale`): quadros de produtos, serviços e custos adicionais. `createSale` aceita `extras` (`[{description, amount}]`): grava em `sales.extras` (JSON) e a soma em `surcharge`; sem `extras`, vale o `surcharge` enviado. `Quotes::convert` manda os custos adicionais do orçamento como `extras`.
- Produtos têm `type` = `produto` | `servico`. Serviço não mexe em estoque; custo fica em `avg_cost`.
- Produção, ficha técnica e tipo `insumo` foram **removidos** (v1.10.0): `DB::upgrade()` converte insumos em produto e `recipe_mode` para `estoque`. A tabela `recipe_items`, as colunas `recipe_*` e os tipos de movimentação `producao`/`consumo_producao`/`consumo_venda` ficam só para o histórico; não use em código novo.
- Ordem de compra salva abre em visualização, como o orçamento: "Editar" grava `sessionStorage.poedit` e reabre editável (só `rascunho`/`enviada`); Salvar e Cancelar voltam à visualização. Ações em massa na lista: `PurchaseOrders::bulk($ids, 'status'|'delete', $status, $data)` (`POST purchases_bulk`, até `BULK_MAX`; mudanças de status seguem `PurchaseOrders::TRANSITIONS`, erros voltam em `errors`).
- Ordem de compra (`PurchaseOrders`, `app/lib/purchases.php`) é só o pedido ao fornecedor: não mexe em estoque nem no financeiro. `pedido.php` é público, acessado pelo `public_token` (o fornecedor confirma por ele).
- Financeiro (`Finance`, `app/lib/finance.php`): tabela `financial_entries` (type `receber`|`pagar`, status `aberto`|`pago`|`cancelado`; "vencido" é calculado). `Inventory::createSale` chama `Finance::fromSale` (recebido) e `cancelSale` chama `Finance::cancelSale`. Lançamentos com `sale_id` não são editados à mão. Fluxo de caixa usa `paid_at`/`paid_amount` (realizado) e `due_date`/`amount` (previsto); saldo inicial na setting `cash_opening_balance`.
- Nota de compra com duplicatas (`<cobr><dup>` no XML, quadro FATURA no DANFE) → `installments` no resultado do parser; `Invoices::confirm` com `payables` chama `Finance::fromInvoice` (`financial_entries.invoice_id`). `revert` bloqueia se houver parcela paga e apaga as em aberto.
- Exclusão de produto/serviço: `Inventory::deleteProduct` apaga se nunca foi usado; senão grava `products.deleted_at` (e `active = 0`). `GET products` sempre filtra `deleted_at IS NULL`. Orçamentos/ordens antigos mantêm o item (só aceitam item excluído que já estava neles); venda nova recusa.
- Importação só aceita nota emitida para o CNPJ da empresa (`company_document`): os parsers devolvem `recipient_doc`; CNPJs aceitos = principal + lista de CNPJs aceitos (`company_branches`, JSON `[{cnpj,name}]`, ver `Settings::companyDocs()`; editados em Configurações → Notas fiscais) ou qualquer um com `invoice_cnpj_mode = qualquer`; `Invoices::recipientError()` é usado em `suggest()` (mostra o bloqueio) e em `confirm()` (bloqueia no servidor). `kind = manual` não é verificado.
- Formas de pagamento: tabela `payment_methods` (`PaymentMethods`, `app/lib/payments.php`). Registros guardam o `code`; nomes via `PaymentMethods::label()` / `payment_labels` no `GET meta`. Validar com `PaymentMethods::check($code, $valorAntigo)` (aceita a antiga mesmo desativada). Usada não se apaga, só desativa. Parcelamento: `max_installments` e `interval_mode` (`fixo` = 30 dias | `livre`); `PaymentMethods::installments()` valida e `PaymentMethods::plan()` monta/valida o plano (`installment_plan` JSON em `sales` e `quotes`); `Finance::fromSale` cria uma conta a receber por parcela. Entrada: `installment_entry` (a entrada é a 1ª linha do plano, com `entry: true`, vence no dia e conta como um dos pagamentos no máximo da forma). Na tela, parcelas/entrada/intervalo vêm da condição de pagamento (`applyTermToInstallments`); não há seletor manual. O valor da entrada é digitado no orçamento/venda (campo `entryval` do `installmentBox`, em R$ ou % pelo seletor `entrymode`; o plano salvo guarda só os valores); a condição só marca que tem entrada (`entry_percent` não é mais usado na tela).
- Condições de pagamento: tabela `payment_terms` (`PaymentTerms`, `app/lib/terms.php`), em `GET meta` como `payment_terms`. Registros (orçamento, venda, ordem) guardam o texto. Campo com `data-create="term"` permite cadastrar pelo próprio campo (`COMBO_CREATE` em `app.js`). Criar: perm orcamentos/vendas/compras; editar/excluir: admin. A tela fica em Cadastros → Pagamento (`viewPayments`, `#/pagamento/condicoes`; aba Formas de pagamento em `#/pagamento/formas`; as rotas antigas `formas-pagamento|condicoes-pagamento` abrem a aba certa).
- Foto de perfil: `users.avatar` (data URL; MEDIUMTEXT no MySQL), recortada em 256 px JPEG no navegador (`pickAvatar`) e validada por `Auth::setAvatar` (PNG/JPEG/WebP, até 200 KB). Não vai no `Auth::user()` (roda em toda requisição): `GET me`/`login` usam `Auth::withAvatar`. Rotas `POST account_avatar` (o próprio) e `POST user_avatar` (admin, `assertCanEdit`); `avatarHtml()` mostra a foto ou as iniciais (menu, Minha conta, lista e formulário de usuários).
- Usuários têm `phone`; o orçamento público mostra nome, telefone e e-mail do responsável (`user_*` em `Quotes::get`).
- Validação dos campos: um ouvinte de `invalid` (captura, em `app.js` e no `cliente/index.php`) troca o balão do navegador por `<span class="field-err">` logo depois do campo (classe `is-invalid`), com texto em português; some quando o campo fica válido. Use `required`/`type`/`minlength` normalmente.
- Telefones: máscara automática no navegador para todo `input[type=tel]` ou com `name`/`id` terminando em `phone` (`phoneMask` em `app.js`) e no servidor com `Customers::phoneMask()` ao salvar (clientes, fornecedores, usuários, empresa, contato do orçamento).
- CPF/CNPJ: máscara no navegador (`docMask`, mesmo motor da de telefone em `MASKS`) para `input[name=document]`, `name` terminando em `_document`/`cnpj`, `data-k=cnpj` ou `data-mask=cnpj|cpf|doc`; sem `data-mask`, até 11 dígitos é CPF. O banco guarda só os dígitos.
- Tributação do produto: `products.fiscal` (JSON), classe `Fiscal` (`app/lib/fiscal.php`): `normalize()` valida e descarta campos que não se aplicam (grupos do ICMS por CSOSN em `CSOSN_GROUPS`, PIS/COFINS/IPI pelo tipo de cálculo); listas em `GET meta` como `fiscal`. Só produtos (serviço grava null); sem a chave `fiscal` no POST, mantém o que existe. `Invoices::confirm` chama `Fiscal::fillFromInvoice` (NCM/CEST/Origem só se vazios; origem 1→2, 6→7). O sistema não emite NF-e.
- Cor de destaque por usuário: `users.accent_color` (null = padrão `#b02a37`), salva por `POST account_accent` (`Auth::setAccent`) e devolvida em `GET me`. `accentCss()`/`applyAccent()` em `app.js` geram as variáveis `--accent*` dos temas claro e escuro, aplicam em `<style id="accent-css">` e guardam o CSS em `localStorage.accentCss` (o `index.php` aplica antes de desenhar). Seção Aparência de Minha conta (`viewAccount` chama `viewAppearance`; `#/aparencia` abre Minha conta): tema e cor juntos, sem permissão especial. Configurações só tem itens de administrador, então o menu some para os outros. PDFs e páginas públicas usam a cor padrão. Use sempre `var(--accent…)` no CSS, nunca a cor fixa.
- Marca e códigos do produto: `products.brand`, `products.mfr_code` e tabela `product_refs` (referências cruzadas: `manufacturer`, `code`, `code_norm`). `Inventory::codeNorm()` (só letras e números, maiúsculas; igual a `codeNorm` no `app.js`) e `Inventory::searchSql()` (busca de produtos: nome, marca, localização, código de barras, SKU/fabricante/referências normalizados). `saveProduct` só mexe em `brand`/`mfr_code`/`refs` se a chave vier no POST. `GET products` devolve `refs`/`refs_norm` para as buscas no navegador (`productCodeMatch`).
- Observações do produto: `products.description` (texto livre, aba Observações). Valor de compra manual: `Inventory::setCost()` troca `avg_cost` e grava movimento `ajuste_custo` (quantidade 0, nota com valor antigo e novo); `saveProduct` chama quando a edição manda `avg_cost` (o front só manda se o campo mudou).
- Estoque inicial: `saveProduct` de produto novo aceita `initial_stock` e chama `Inventory::move(..., 'entrada', ...)` com o custo inicial (`avg_cost`) e nota "Estoque inicial"; na edição é ignorado.
- Importação de produtos por planilha: `app/lib/import.php` (`XlsxReader` lê .xlsx sem bibliotecas, com zip próprio; `ProductImport::read/preview/import`). Rotas `POST products_import_preview` (arquivo, devolve `rows`/`skipped`/`errors`/`noname`) e `POST products_import` (lotes de até `ProductImport::BATCH_MAX`; o front manda 300 por vez). SKU já existente é pulado. Estoque > 0 → `move('ajuste')` com `at` = data da coluna F (ou hoje); estoque 0 → movimento `entrada` de quantidade 0. Desfazer: `ProductImport::history()` (`GET products_imports`, admin; produtos com movimento de nota de importação, por dia de `created_at`) e `ProductImport::undo($dia)` (`POST products_import_undo`, admin) apaga de vez os não usados depois (movimentos fora da importação ou itens de venda/orçamento/nota/ordem). `GET products&all=1` devolve todos (sem `description`/`fiscal`) para as buscas no navegador; sem `all` a lista vai até 1000.
- Configurações de Orçamento, Vendas, Notas fiscais e Ordens de compra: uma tela para cada, direto no menu (sem submenu). Orçamento = `viewQuoteSettings` (`#/orcamento-config`, junta `viewQuoteBehavior` e `viewQuoteStatuses`; as rotas antigas `orcamento-status|comportamento` abrem a mesma tela).
- Comportamento (Configurações → Vendas / Notas fiscais / Ordens de compra; `viewSaleBehavior`, `viewInvoiceBehavior`, `viewPoBehavior`, gravam por `POST settings`): chaves `sale_*`, `invoice_*` e `po_*` em `Settings::DEFAULTS` (validadas em `Settings::save`, listas em `CHOICES`/`FLAGS`) e enviadas a todos em `GET meta` como `behavior` (`Settings::behavior()`; no front `BH()`). Vendas: `sale_negative_stock` (`createSale` passa `allow_negative`), `sale_cash_open` (`Finance::fromSale` à vista em aberto), `sale_max_discount` (não admin, venda direta), `sale_cancel_admin`/`sale_cancel_days` (`Inventory::checkCancelRules`; front `canCancelSale`), `sale_default_customer|method|notes`. Notas: `invoice_cnpj_mode`, `invoice_payables`, `invoice_pay_method`, `invoice_fiscal` (modo de `Fiscal::fillFromInvoice`), `invoice_price`/`invoice_markup` (o item da nota manda `sale_price`, aplicado em `Invoices::confirm`). Ordens: `po_delivery_days|default_method|default_terms|default_notes` (em `purchase_defaults`), `po_statuses` (nome/cor; `PurchaseOrders::label()`, front `syncPoStatus()` sobre `PO_STATUS_DEFAULT`), `po_supplier_confirm` (`pedido.php`/`supplierConfirm`) e `po_message` (`poMessage` em `sendPurchase`).
- Exclusão de clientes, fornecedores, equipamentos, tipos de tarefa e questionários (`Removals`, `app/lib/deletion.php`; rotas `POST customer_delete|supplier_delete|equipment_delete|task_type_delete|questionnaire_delete`, admin): nunca usado (`Removals::REFS`) apaga de vez; usado grava `deleted_at` (e `active = 0`). Excluído some das listas (`deleted_at IS NULL` em `GET customers/suppliers`, `Equipments::list`, `TaskTypes::list`, `Questionnaires::list`), não pode ser editado e não pode ser escolhido em registro novo (`Removals::check($tabela, $novo, $atual)`: só vale se o registro já usava o mesmo item); orçamentos, vendas, OS, notas, ordens e lançamentos continuam mostrando o nome. Cliente excluído perde o acesso ao portal; "Consumidor final" não se exclui. Questionário excluído sai dos tipos de tarefa, mas a OS que respondeu continua mostrando. Cadastrar de novo o CPF/CNPJ de um excluído traz o mesmo registro de volta (`Customers::save`; nota importada faz o mesmo com o fornecedor). No front, `deleteRecord()` e `custOptions()` (o cliente atual aparece no select mesmo excluído ou inativo).
- Campos só de número: `input[data-num]` (`dec` = algarismos, vírgula, ponto e "-" no começo; `money` = máscara que começa pelos centavos, `moneyMask`/`moneyMaskVal`), nas respostas Numérica/Monetária, na "Resposta esperada" das condicionais e nos campos de valor do sistema.
- Tabelas novas também entram em `Backup::TABLES`.
- Backup no Google Drive: `GDrive` (`app/lib/gdrive.php`), por um Google Apps Script do próprio usuário (sem OAuth nem Google Cloud). `GDrive::script()` gera o código com a chave secreta (`gdrive_key`); o usuário publica como App da Web e cola o URL `/exec` e o link da pasta (`GDrive::connect` testa com `acao: teste`). O envio (`acao: enviar`) leva o .sql.gz em base64 e o script apaga (lixeira) os antigos com o prefixo `bkp-db-` (`GDrive::FILE_PREFIX`, genérico; o download manual usa o mesmo nome) e os antigos `backup-estoque-` (`OLD_PREFIXES`, enviados em `prefixos`) além de `keep`. Configurações na tabela `settings` com prefixo `gdrive_` (fora do `Settings::all()` e fora do `Backup::sql()`, que também não apaga essas linhas ao restaurar). Agenda (`freq` off|daily|weekly, `hour`, `weekday`, `keep`) conferida por `app/cron.php` (só CLI), chamado no fim do `deploy/auto-deploy.sh` a cada ~15 minutos (a hospedagem não aceita menos que 15; ela reescreve `*/5` para `*/15`, `*/16`…). `GDrive::$transport` troca o HTTP nos testes. Rotas `GET gdrive`, `POST gdrive_config|gdrive_connect|gdrive_disconnect|gdrive_run` (admin).
- Orçamento (`Quotes`) não mexe em estoque; `convert()` cria a venda via `Inventory::createSale` (descontos → `discount`, custos adicionais → `surcharge`). Na conversão, os vencimentos do plano andam os dias entre `request_date` e a data da venda (`Quotes::shiftPlan`; no front, `quoteShiftDays`/`shiftPlanDates` em `convertQuote`). `orcamento.php` é público, acessado pelo `public_token` (`&download=1` baixa o PDF; `&pdf=1` abre a impressão).
- Status de orçamento: tabela `quote_statuses` (`QuoteStatuses`, `app/lib/qstatus.php`), em `GET meta` como `quote_statuses` (o front reconstrói `Q_STATUS` com `syncQStatus()`). `SYSTEM` = os 7 de sistema (código fixo, regras próprias; renomear/cor/ordem, sem excluir/desativar); criados pelo usuário recebem código `st_<id>`. Validar com `QuoteStatuses::check($code, $atual)`; escolhíveis = `selectable()` (ativos, sem `vendido`); fechados = `CLOSED`.
- Orçamento sempre tem cliente ou lead (com nome). Só cliente cadastrado aprova (`save`, `setStatus`, `mark`, `clientRespond`) e gera venda (`convert`). Salvo abre em visualização; "Editar" grava `sessionStorage.qedit` e reabre editável. "Mais ações": `quote_mark` (`Quotes::mark`, status das settings `quote_on_sent`/`quote_on_approved`/`quote_on_refused`, tela Configurações → Orçamento), `quote_delete` (não exclui vendido) e "Duplicar" (copia para `sessionStorage.quoteCopy` e abre `#/orcamento/novo` sem cliente, sem salvar).
- Filtros das listas de orçamentos e vendas: `Reports::listFilters($in, $w, $p, $cols)` (from/to de criação, customer texto, min/max, user_id); no front `filterPanelHtml` + `bindFilterPanel`.
- Ações em massa: `Quotes::bulk($ids, $acao, $status)` (`POST quotes_bulk`, até `Quotes::BULK_MAX`; cada orçamento à parte, erros voltam em `errors`). PDF sem biblioteca: `app/lib/pdf.php` (`SimplePdf`, `ZipWriter`, `QuotePdf::render`); `GET quote_pdf&id=` devolve o PDF e `GET quotes_pdf_zip&ids=` o .zip. Front: `typeConfirm()` pede a palavra digitada.
- Permissões por módulo (v3.1.0): `Auth::MODULES` = módulo → [nome, texto do Visualizar (null = sem), ações]; códigos `modulo` (visualizar) e `modulo.acao` (ex.: `ordens.hours`, `equipamentos.delete`, `orcamentos.convert`). `Auth::perms()` (lista plana) e `Auth::modules()` (tela, em `GET me` como `perm_modules` e em `GET profiles` como `modules`). Gravadas com o marcador `_v2` (`Auth::normalizePerms`: só códigos válidos, ação liga o Visualizar do módulo); listas antigas sem `_v2` viram o novo formato por `Auth::expandLegacy` (`DB::upgrade` → `Auth::upgradePerms`). Cada usuário tem um perfil (`users.profile_id` → `permission_profiles.permissions`); sem perfil vale `users.permissions` (NULL = todas); admin sempre todas (`Auth::permsOf`). Rotas usam `Auth::requirePerm('modulo.acao')` (vários argumentos = qualquer um); no front, `can('modulo.acao')` esconde menu e botões e `ROUTES` tem a permissão de cada tela. Toda rota nova precisa de permissão (e ação nova entra em `MODULES`). Tela: Configurações → Sistema → Permissões (`viewPermissions`, `profileForm` com sanfona por módulo e "Marcar todos"). Configuração geral (tabela `settings`, inclusive `po_default_notes` e `cash_opening_balance`) só por administrador; quem não é administrador só muda a própria Aparência.
- OS do técnico: sem `ordens.all` o usuário só vê e mexe nas OS em que é o técnico (`ServiceOrders::$onlyTech`, definido no `api.php`; filtra `list`, `get`, `agenda`, `dashboard`, `techTasks`/`techHome`; OS criada/reagendada por ele fica com ele). OS concluída só muda com `ordens.after_checkout` (`ServiceOrders::$afterCheckout`, `assertChangeable`, usado em `OrderExec::editable` e no `save`). Na ficha (`viewServiceOrderForm`) cada aba só libera com a sua permissão (`soPerm`/`permLock`).
- App do técnico x versão completa: `tkOn()` = celular + perm `ordens` + (sem `app.switch` ou `tkMode` ≠ `off`). Só quem tem `app.switch` vê "Versão completa" na gaveta e "App do técnico" no menu (este só no celular). Telas da versão completa abertas pelo app (Minha conta, Equipamentos, Clientes…) abrem dentro do app (`tkHost`, chamado pelo `route()`); `#/ordem/ID` no app vira `#/m/os/ID`.
- Usuários: e-mail validado por `Auth::cleanEmail()`. Excluir (`POST user_delete`, `Auth::deleteUser`): apaga se não aparece em `Auth::USER_REFS` (vendas, notas, orçamentos, financeiro, ordens, movimentos); senão desativa. Pela tela/API um administrador só altera a si mesmo e membros (`Auth::assertCanEdit`, `ADMIN_OTHER`); administrador não é rebaixado, desativado nem excluído pela tela/API (`Auth::ADMIN_LOCKED`), só por `app/users-cli.php` (CLI), que nunca deixa zero administradores ativos. Tabela nova que guarde usuário entra em `USER_REFS`.
- Portal do cliente: pasta `cliente/` (`cliente/index.php`, páginas em PHP, sessão própria `estoque_cliente` só nessa pasta, CSRF por formulário, tema claro/escuro em `localStorage.portalTheme`, separado do `theme` do sistema) e classe `Portal` (`app/lib/portal.php`). Acesso na tabela `customer_portal` (hash da senha, hash do convite + validade de 7 dias, último acesso), fora de `customers` para não vazar em `SELECT *`. Pedidos de correção em `portal_requests`. Login = `customers.document` + senha, com o limite de tentativas da `login_attempts` (ip com prefixo `portal:`). O cliente só vê orçamentos fora de `Portal::HIDDEN_QUOTE_STATUS` (ou já enviados), que abrem no `orcamento.php?t=…&portal=1`; compras e parcelas (`financial_entries` receber) só dele. Rotas `POST customer_portal_invite|customer_portal_revoke|portal_request_done` (perm clientes); `GET customer` devolve `portal`. `.cpanel.yml` copia `cliente/`. A entrada do portal (login e convite) usa o mesmo visual da tela de login do sistema (classes `lg-*`, CSS copiado dentro do `cliente/index.php`, que não carrega o `assets/style.css`).
- Clientes e fornecedores usam a mesma classe `Customers` (parâmetro `$table` = `customers` | `suppliers`) e o mesmo `customerForm(..., { entity: 'supplier' })`.
- Mudanças de banco: novas colunas/tabelas entram em `DB::schema()` **e** num bloco de `DB::upgrade()` (bancos já instalados se atualizam sozinhos).
- A importação de notas segue o fluxo: `parseXml`/`parseDanfePdf`/`fetchNfce` → `suggest()` (casa itens via `supplier_map`, código de barras ou nome) → o usuário confere → `confirm()`.

- Pergunta condicional: "Essa é uma pergunta condicional" só aparece quando há pergunta anterior que pode ser mãe (com texto e tipo em `Questionnaires::COND_PARENT_TYPES`: numérica, check, monetária, data, itens, hora, múltipla). `cond = {question, op, value}`: "Apresentar quando", "Condição" (por tipo da mãe em `COND_BY_TYPE`: Menor/Maior/Menor ou igual/Maior ou igual/Igual/Diferente para número, dinheiro, data e hora; Igual para check, com Verdadeiro/Falso = `sim`|`nao`; Igual/Diferente para itens; Contém todos/Contém um/Não contém um para múltipla, com lista) e "Resposta esperada" no formato da resposta (`condValue`). Avaliação em `Questionnaires::condMatch` = `qCondMatch` no `app.js` (mãe precisa estar visível e respondida; check sem marcar = Falso). Mãe depois da condicional é recusada ("A pergunta N depende da pergunta M…"). No editor, trocar o tipo da mãe remove a condição (tipo sem condições) ou limpa condição e resposta, com aviso; duplicar copia a condição; campos vazios mostram "Este campo é obrigatório".
- Execução da OS (`OrderExec`, `app/lib/execution.php`): respostas dos questionários em `so_answers` (JSON por questionário; `normalizeAnswers` valida pelo tipo e descarta perguntas escondidas pela condição; `visibleMap` = `qVisible` no `app.js`), situação do questionário por `OrderExec::progress` (preenchidas/total das perguntas visíveis; respondido = ao menos uma preenchida; apagar todas as respostas apaga a linha de `so_answers` e volta a "não respondido"; no front `qStatusHtml`, refeito a cada mudança), relato/assinatura/km/assinante em `service_orders`, fotos em `so_photos`, itens (produto/serviço/custo, não mexem em estoque) em `so_items`, histórico de status em `so_events` (todo `setStatus`/`save`/`reschedule` grava; `hours()` monta o controle de horas) e envios em `so_sends`. Concluir chama `OrderExec::pending()` (obrigatoriedades do tipo de tarefa + perguntas obrigatórias) e bloqueia se houver pendência; depois `onConcluded` envia OS/pesquisa por e-mail (falha fica registrada e não bloqueia). `os.php` é público pelo `public_token` (OS digital + pesquisa de satisfação, `&pesquisa=1`). E-mail pelo servidor: `Mailer::send` (`mail()`; `Mailer::$transport` nos testes).
- Controle de horas (`OrderExec::hours/saveHours`, `POST so_hours_save`): mostra só as atividades (`ACTIVITY`: deslocamento = status `a_caminho`, check-in, início/fim da pausa, check-out; abertura e agendamento ficam só no histórico). Totais de deslocamento, pausa e trabalho. Na edição: data/hora, motivo da pausa, justificativa (opcional), excluir (marca `deleted_at`) e "Adicionar atividade" com as próximas possíveis (`nextKinds`, igual a `hrNext` no `app.js`). A sequência segue `FLOW`; a OS fica no status da última atividade (check-out conclui e exige as pendências). Guarda `original_at`, `edited_by`, `edited_at`; "Histórico completo" mostra tudo, inclusive excluídas.
- Ficha da OS (`viewServiceOrderForm`): abas Detalhes, Relato, Questionários, Valores, Orçamentos, Pendências, Controle de horas e Envios. **Um só "Editar" no topo** libera todas as abas (cada aba registra sua trava em `locks` e seu salvamento em `savers`); "Salvar" grava só o que mudou, aba por aba (fotos e itens incluídos/removidos ficam pendentes até salvar); "Cancelar" recarrega a ficha.
- OS não fatura (v2.0.0): o status `faturada` foi removido (`concluida` é o fim; o `DB::upgrade()` converte as antigas). Quem fatura é o orçamento. Orçamento → OS: "Mais ações → Gerar ordem de serviço" (`sessionStorage.soFromQuote`, abre `#/ordem/nova` com cliente, origem `orcamento`, `quote_id` e descrição). OS → orçamento: "Abrir orçamento" (`sessionStorage.quoteFromOs`: cliente, itens de Valores como itens, custos como `extras`) e o orçamento guarda `quotes.service_order_id` (só na criação; a OS precisa ser do mesmo cliente). `Quotes::get` devolve `service_orders` e `OrderExec::detail` devolve `quotes`.

- Peças e Serviços da OS (aba `valores`, antes "Valores"; `so_items`, `OrderExec::KINDS` = Peça/Serviço/Custo adicional): peça e serviço vêm do cadastro (`product_id`); item não cadastrado entra com `new_item` e `product_id` NULL = aguardando revisão (`items()['review']`, aviso na OS e no painel `items_review`). Revisão (`OrderExec::reviewItem`, `POST so_item_review`; peça → perm produtos, serviço → perm servicos): cadastrar (cria o produto/serviço com nome, unidade e preço), vincular a um item já cadastrado ou recusar (tira da OS). Lista geral em Cadastros → Itens para revisar (`#/revisao-itens`, `GET so_items_review`; perm `revisao` no front = produtos ou servicos). Abrir orçamento a partir da OS exige tudo cadastrado (`openQuote` no front e `Quotes::save` com `service_order_id`). Front: `reviewItemModal`.
- Questionário não escolhe equipamento (v3.0.0): o equipamento é o dos Detalhes da OS; `allow_equipment`/`equipment_required` ficam sempre 0 (colunas só para o histórico).
- Tipo de tarefa: vários questionários numa lista ordenada (▲ ▼ no formulário); `questionnaire_ids` guarda a ordem e a OS mostra os questionários nessa ordem.
- App do técnico: depois do check-out (OS concluída), no celular tudo fica só para consulta (aviso `.tk-lock`, sem salvar/adicionar/remover); alterar só pela versão completa.
- Máscara de valor em todo campo de dinheiro (`data-num="money"`): começa pelos centavos; só na digitação (`isTrusted`); ao entrar no campo, o valor já escrito é normalizado para 2 casas. Campos de custo unitário com 4 casas (custo do produto, custo na ordem de compra) e descontos em R$ ou % não usam a máscara.
- Painel (`viewDashboard`, `GET dashboard`): com perm ordens, `ServiceOrders::dashboard($userId)` (em aberto por status, sem agendamento, atrasadas = prazo vencido ou agendada no passado sem começar, agenda de hoje e quantas são do usuário, concluídas hoje/no mês, média da pesquisa de satisfação do mês, concluídas nos últimos 30 dias sem orçamento); com perm orcamentos, `quotes` (aprovados aguardando venda e orçamentos abertos por OS no mês). Front: `dashOrdersHtml`.
- App do técnico (celular): rotas `#/m` (Início), `#/m/agenda` (Calendário da semana / Mês, Minha agenda ou da equipe, filtros por situação), `#/m/os/ID` (Detalhes, Relatório = checklist Fotos/Questionário/Quilometragem/Relato/Assinar e enviar + Controle de Horas, Pendências; barra com A caminho/Check-in/Pausar/Retomar/Check-out) e `#/m/os/ID/<página>` (fotos, questionarios, questionario/QID, km, relato, assinar, pausas, cliente, valores, orcamentos). Questionário no celular: Todas / Foco (uma pergunta por vez) / Sem resposta. Código em `app.js` (`tk*`, `TK_ROUTES`, `tkRoute`, chamado pelo `route()`), CSS `.tk-*`. Abre sozinho em tela até 760 px para quem tem perm ordens (`tkMode` em `localStorage`; "Versão completa" no menu grava `off`; "App do técnico" no rodapé do menu volta). API: `GET tech_home` e `GET tech_tasks` (`ServiceOrders::techHome/techTasks`, com `all=1` para a equipe); o resto usa as rotas da OS.
- Menu lateral: ao trocar de tela, só fica aberto o grupo (e subgrupo) da tela atual; os outros se recolhem (`route`). Botão "Novo": OS, orçamento, venda, ordem de compra (`NEW_ITEMS`).

## Instalação híbrida (cPanel ou VM Debian 13)
- Repositório público: instalação sem token nem link "raw" (clone por `https://github.com/pepehend/ciclos-erp.git`).
- cPanel: Git Version Control clona o repositório; `.cpanel.yml` publica (o `install.php` só vai enquanto não existe `app/config.php`) + `deploy/auto-deploy.sh` (Cron a cada 15 minutos).
- Servidor próprio (LXC/VM Debian 13): `deploy/debian/install.sh` (mesmo modelo do instalador do estoque-standalone: roda de novo com `sudo` se não for root, roda uma cópia temporária quando chamado de dentro de `/opt/ciclos-erp`, sem argumentos). Clona por HTTPS em `/opt/ciclos-erp`, cria o banco MariaDB e grava o `app/config.php`, publica em `/var/www/ciclos-erp` com `deploy/auto-deploy.sh --forcar`, prepara o banco e cria o administrador pelo terminal (`deploy/debian/setup.php`, `--admin-se-vazio`; o `install.php` é apagado), Apache com `remoteip` (Cloudflare Tunnel) e `/etc/cron.d/ciclos-erp` (auto-deploy a cada 5 minutos + `backup.sh` às 3h em `/var/backups/ciclos-erp`, `bkp-db-*.sql.gz`, 30 dias). Outros scripts: `restore.sh`, `users.sh` (→ `app/users-cli.php` como www-data), `tunnel.sh`. Grava `deploy/servidor.conf` (fora do Git: `MODE=vm`, `DEPLOYPATH`, `OWNER`, `LOG_DIR`), que o `auto-deploy.sh` lê para pular o `uapi`, copiar para a pasta certa, acertar permissões (root:www-data, `data/` do www-data, `config.php` 640), rodar o `setup.php --quieto` depois de publicar e rodar o `app/cron.php` como `www-data`; registro em `/var/log/ciclos-erp/update.log`. Arquivo novo que vai para o site entra no `.cpanel.yml` (vale para os dois).

## Fluxo de trabalho (Git)
- Branch fixa de trabalho: **`development`** (antes era `desenvolvimento`, que travou no GitHub). Não crie outras branches.
- Antes de começar: `git fetch origin && git checkout development && git merge origin/main` (traz o que já foi aprovado).
- Commite e envie para `development`. Existe sempre **um** pull request `development → main`; se já estiver aberto, os commits novos entram nele (atualize a descrição). Se não houver, abra um novo.
- O Pedro aprova com **Merge** no GitHub; o Cron do cPanel publica a `main` em até ~15 minutos.
- **Antes de dizer que um commit entrou num PR aberto, confira** com `gh api repos/pepehend/ciclos-erp/pulls/N --jq .state` (o PR pode ter sido aprovado nesse meio tempo). Se estiver fechado, abra um PR novo; nunca edite a descrição de um PR já fechado.

## Versionamento
- A versão fica em `APP_VERSION` (`app/bootstrap.php`) e aparece no rodapé do menu. Começa em `1.0.0`.
- Primeiro número (**maior**): muda quando há alteração que quebra compatibilidade (ex.: remoção de funcionalidade ou de dados).
- Segundo número (**menor**): muda a cada funcionalidade nova. Ao subir este número, o terceiro volta a `0`.
- Terceiro número (**correção**): muda a cada correção de erro sem funcionalidade nova.
- Cada PR que muda o comportamento do sistema atualiza `APP_VERSION` no mesmo commit.

## Telas em paralelo
- A tela de entrada da equipe (`renderLogin` em `assets/app.js`) e a do portal do cliente (`cliente/index.php`) devem ter o mesmo texto de destaque e o mesmo subtítulo. Quando mudar uma, mude a outra no mesmo commit.
